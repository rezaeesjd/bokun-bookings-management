# Version 1.4.1 — Hotfix: blank Analytics dashboard after large imports

## What broke

After a large fetch/import followed by an Analytics rebuild, opening the
dashboard could return a **blank page** (a PHP fatal — memory exhaustion —
rather than HTML).

## Cause

The Analytics **Records** enrichment (links column + refund toggle, added in
1.3.6) loaded **every booking's post meta into memory**: it primed the full
meta cache for all matched rows (`_prime_post_caches($ids, false, true)`) and
then called `get_post_meta()` per row. That cost scales with
`rows × meta-per-booking`, and the 12-month retention window (1.4.0) widened
the row set enough to blow past the PHP memory limit on real data — so the
render died before emitting any markup.

## Fix

The enrichment now reads only the two meta keys it actually needs
(`productBookings_0_parentBookingId` for the Bokun link,
`_user_channel_refunded` for the refund state) in a **single bounded bulk
query**:

- Post **objects** are primed (`_prime_post_caches($ids, false, false)`), not
  their meta.
- One `SELECT post_id, meta_key, meta_value … WHERE post_id IN (…) AND
  meta_key IN ('productBookings_0_parentBookingId','_user_channel_refunded')`
  replaces the per-row `get_post_meta()` loop.
- Memory and query count are now **O(1) in the number of rows** — one query
  whether the window holds 50 bookings or 50,000.

No data model, net-revenue formula, link format, or refund behaviour changed;
the Records table renders exactly as before, just without the memory blow-up.

## Tests

Analytics interaction suite extended to **22 checks**, including a regression
guard that asserts the enrichment issues **exactly one** meta query regardless
of row count (6 rows → 1 query). Full suite green (dashboard-access 35,
access-control 28, messages 31, booking-webhook 69, WordPress integration).
